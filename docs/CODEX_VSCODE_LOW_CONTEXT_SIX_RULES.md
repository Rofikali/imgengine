**Status:** owner-requested standing agent practice, docs-only proposal (2026-11-17). **Goal:** reduce *unnecessary* Codex context/allowance consumption while preserving engineering, security, required CI, and owner approval. **Not** a guarantee of token savings or an actual token/billing measurement. This policy affects the work style of agents who read the repo; it does not set Codex account limits or automatically modify model configuration.

**Windows host versus local Docker runtime (2026-11-19):** “Local workspace first” means use **local source/Git**; do **not** run the project toolchain in Windows. Every new session checks active `next.md` + worktrees + scoped AGENTS, and checks P7 Docker files **before testing**. Read only necessary sections; reuse verified environment state. Report BLOCKED/NOT RUN if Docker fails; retain all exact-SHA CI/security and owner approval gates.

**Read only when applicable:** [short live milestones](../next.md), [root AGENTS](../AGENTS.md), [Skill 20/21](../skills.md), [existing minimal-context CI policy](CI_FIRST_MINIMAL_AI_CONTEXT_POLICY.md), [product/infra and post-reset usage protocol](IMGENGINE_PRODUCT_INFRA_MILESTONE_AND_CODEX_USAGE_PROTOCOL.md). ## Six binding rules for VS Code Codex sessions

1. **Local workspace first:** For source, working-tree diffs, branch history, modifications, testing and source analysis, use **local VS Code workspace + local Git commands**. Use a GitHub connector only for *remote-only* facts/actions such as PR publication, PR review state, head SHA, CI check conclusions and merge confirmation. If local file content exists at the relevant SHA, do **not** download the same source/diff through the connector without a specific reason. Reconcile that the local working-tree SHA and remote PR SHA are different when they are.
2. **Read minimal project context:** Start with **short `next.md`**, Git status/PR metadata needed for task selection, root instructions actually made available to the agent, the applicable nested AGENTS, the current bounded milestone contract, and directly relevant source/test files. Access `next-history.md`, large archives, broad skills, entire test trees or all docs **on demand** only. Do not mistake avoiding unnecessary reads for ignoring binding security/deployment rules. Agent-injected instructions may be automatic and cannot always be suppressed.
3. **GitHub only where valuable:** When remote access is needed, request **small metadata**: PR number, status, current head SHA, changed filenames, CI job name/status/conclusion and run links. Use local `git diff` to inspect known changes. Fetch individual GitHub patch hunks or failing steps **only when needed for a particular review or divergence**; don't routinely retrieve whole PR diffs, all remote file contents, workflows, successful logs or repeatedly poll pending checks. Opening/publishing an actual PR still requires GitHub and applicable permissions.
4. **Execute tests fully but read results briefly:** Run focused local tests appropriate to the changed scope and exact SHA; capture full output in local ignored logs/CI artifacts. Report command, PASS/FAIL/NOT RUN, target SHA, and concise outcome. On failure inspect relevant **40–60 lines** first and expand only when evidence requires it. Preserve all seven existing GitHub PR CI jobs, native sanitizer/fuzz/ABI/FFI gates when applicable and exact-head release requirements; **never skip tests, hide errors or downgrade checks to save tokens**. Don't push many intermediate status-only commits that retrigger full CI; batch one accurate PR checkpoint when possible.
5. **Match model/reasoning to actual risk:** For routine Nuxt UI, documentation, PR status and small local tasks, **consider** the lowest-cost available model and standard speed/lower reasoning effort *if supported in the user's current Codex VS Code UI*. Reserve medium/high reasoning for native concurrency, C17/Rust FFI, hard bugs, architecture/security and high-stakes reviews. **This is a recommendation, not authorization to silently change user settings**, nor a guarantee that any specific mode has a fixed or lower cost; compare actual usage and quality. A lighter model that causes repeated failed iterations may be more expensive in total.
6. **Measure instead of guessing:** Once **both relevant 5-hour and weekly allowances** have adequate remaining capacity, the owner may privately compare matched **read-only** local-only versus GitHub-heavy Codex sessions using the *same model, effort, task scope and clean session conditions*. Record before/after allowance **percent remaining**, timestamps/reset crossings, tool calls, approximate returned text size, and any delay in usage reporting. Percent delta is **not a precise token invoice**; shared Work/other agent activity or UI lag can invalidate the comparison. [Detailed private experiment protocol](IMGENGINE_PRODUCT_INFRA_MILESTONE_AND_CODEX_USAGE_PROTOCOL.md#3-codex-vs-code-plus-usage-controlled-beforeafter-comparison). Never commit personal account usage, payments or screenshots to this public repository.

## Startup / completion short protocol

**Startup:** Inspect current `main` and local checkout/branch and short `next.md`; identify **one** READY child milestone inside the proper Free/Pro/Studio/API product parent or P7/P8/P12/P14 infra track. Check that earlier work is not already merged. Use locally present code for analysis; remote GitHub call only for specific missing remote facts. Keep full history archived, not copied into the prompt.

**While implementing:** Make a small reviewed change; run focused tests appropriate to the affected boundary; retain logs locally; don't manually repeat GitHub's entire already-required CI. Catch failures accurately and narrow scope rather than expanding context unnecessarily.

**Publishing:** One coherent PR and concise summary, let the full existing seven checks complete. For CI, retrieve check summaries, not successful logs. Fix failed step and rerun exact-head checks; no automatic merge or deployment.

**Handoff (8–12 lines max when green):** task/product parent, changed scope, tested SHA, local tests, PR + CI link and status, security/privacy gaps, precise next READY child. Document merge only after GitHub confirmation and product release only after a real approved launch. Don't store model tokens, personal allowance or billing details in public files.

## Measurement, safety and scope

- **Cost meters are different:** Codex usage on ChatGPT Plus, optional credits/Work shared allowance, GitHub Actions compute and GitHub Pro/Copilot subscription are separate accounting questions. Reading a large GitHub tool response *can* increase model context; merely running GitHub Actions doesn't itself bill Codex tokens. No exact bill is inferred from text size.
- **Evidence preservation:** No deleting old documentation history, weakening CI, no releasing C17/Rust server publicly from simulated capacity, no unapproved credentials, vendor purchases, ad activation or payment system.
- **Bottleneck exception:** If a remote-only source is missing locally, or a security review genuinely needs the complete patch/CI diagnostics, fetch the minimum sufficient context and record why; never optimize away essential safety or correctness.
- **Validation:** Only owner-provided private Usage data, within a controlled experiment, can demonstrate a before/after allowance difference. Do not claim the repo enforces model selection or actual token quotas.

**Approval boundary:** Applying this guidance in future Codex sessions does **not** authorize editing or merging code beyond the separately selected milestone. This docs PR makes no CI, Docker, application code, GitHub account, subscription, or VS Code configuration changes.
